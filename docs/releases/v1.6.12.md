# NahaN Core v1.6.12

## Summary

Published core routes no longer stop forwarding solely because a 30-second
control-plane refresh deadline passes. The last validated route remains selected
until explicitly replaced or restricted.

## Changes

- Removed automatic refresh-expiry blocking from published source egress routes.
- Applied persistent publication to managed transit next-hop dispatch, without
  introducing unauthorized direct fallback.
- Removed the independent refresh-expiry deadline from destination exit-IP rules.
- Separated encrypted source-route journals into `prepared` and `committed`
  states, preventing interrupted installations from being restored as successful.
- Enabled committed source and destination routes to survive restart beyond
  their former refresh timestamp.
- Preserved snapshot compatibility, revision/digest validation, explicit
  restrictions, withdrawal, routing consent and exit-address ownership checks.
- Added regression coverage for missed refreshes, committed and interrupted
  restoration, explicit restrictions, withdrawal and consent enforcement.
- Documented the new route lifecycle, migration behavior and revocation tradeoff.

## Compatibility and Security

`leaseSeconds` remains refresh metadata, not a forwarding deadline for published
routes. Older journals retain bounded restoration until the first successful
synchronization writes committed state. Startup may still require panel access.

User authorization, subscription expiry, quotas, device leases and independent
credential/principal validity remain unchanged. A disconnected core cannot learn
a new remote withdrawal until communication returns; it retains the last
published route. This is not unlimited offline customer access.

## Validation and Upgrade

Relevant release tests passed. A 31-second no-refresh regression keeps source
and destination routes selected; the same test fails with the previous runtime
installation method. These checks do not prove every production interruption is
resolved.

Use the verified updater and signed `updates.json` catalog. Applying an update
restarts the selected core and can interrupt its connections; use sequential
fleet updates. Verify the binary digest, fresh heartbeat, applied revision and
successful routing synchronization. Rolling back to v1.6.11 restores its
refresh-expiry behavior.
