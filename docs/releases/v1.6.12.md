# NahaN Core v1.6.12

## Summary

This release removes the short refresh-expiry forwarding deadline from
successfully published core routing decisions. Previously, a delayed management
request or interrupted control-plane connection could exhaust a 30-second route
lease and block new connections even while the core process was still running.

In v1.6.12, the last validated, installed route remains selected until an
explicit replacement or restriction is applied. Missing a control-plane refresh
alone is no longer treated as route revocation. This does not remove user
authorization or guarantee that every independent service interruption is fixed.

## Routing Changes

- **Source egress:** published routes no longer stop admitting new connections
  solely because their refresh interval elapsed.
- **Transit dispatch:** managed next-hop selection uses the same persistent
  publication mechanism. No unauthorized direct-route fallback is introduced.
- **Destination exit selection:** installed exit-IP rules remain selected across
  missed control-plane refreshes. Fixing only the source would have left an
  independent destination-side expiry mechanism in place.
- **Synchronization and observability:** refreshes and management error reporting
  continue. Failed requests are not reported as successful renewals.

## Persistence and Restart Recovery

Source route publication now distinguishes an encrypted `prepared` journal,
written before installation, from a `committed` journal written after successful
installation. A committed route is not rejected after restart merely because its
former refresh timestamp has passed. An interrupted preparation must not be
restored as a successfully installed route.

Destination rules are also recorded as committed after successful installation
and encrypted persistence. Exit-IP ownership and selector validation remain
required.

Journals written by older releases retain their previous bounded restoration
behavior until a successful synchronization writes committed state. After an
upgrade, verify that routing synchronization has completed; a running process
alone is not proof that this migration has occurred. Control-plane access may
still be required during core startup.

## Compatibility and Security Boundaries

- Existing snapshot formats and revision/digest checks are preserved. Changing a
  payload without advancing its revision is still rejected.
- `leaseSeconds` remains validated for protocol compatibility and refresh
  scheduling, but is not a forwarding deadline for installed published routes.
- Explicit restrictions, withdrawal, inactive destination selectors, routing
  consent and locally owned exit-address checks remain enforced.
- Missing managed handlers or withdrawn transit routes do not silently fall
  back to an unauthorized direct connection.
- Subscription expiry, quotas, user authorization, registered-device leases,
  credential-delivery scope expiry and destination-principal authorization are
  unchanged. This release does not grant unlimited offline customer access.

**Availability/revocation tradeoff:** a disconnected core cannot receive a newly
issued remote route withdrawal. It deliberately retains its last published
route instead of interpreting management silence as revocation. New validated
changes are applied when communication returns. Independent customer
authorization controls can still deny access during a prolonged control outage.

## Difference From v1.6.11

v1.6.11 prioritized route refresh between sequential management requests and
allowed fresh authorization of an unchanged plan to renew routing before a
separate credential delivery completed. However, its 30-second forwarding
deadline remained in effect. v1.6.12 removes that automatic refresh-expiry
interruption for published routing decisions themselves.

## Validation

- Relevant release tests cover the egress registry, destination policy, manager,
  dispatcher, control plane, updater, routing consent and regressions.
- A 31-second interval with no control-plane requests or local renewal leaves
  both source and destination routes selected without rebuilding the runtime.
- The identical regression test using the previous runtime installation method
  fails after 31 seconds because the source route expires.
- Checks also cover explicit blocking, withdrawal, same-revision payload
  rejection, committed restoration beyond the former refresh timestamp,
  interrupted prepared restoration and routing-consent enforcement.
- These are bounded software checks, not proof that every intermittent
  production failure has been eliminated.

## Upgrade and Rollback

Use the existing verified updater and signed `updates.json` catalog. Download
and preparation do not themselves require a core restart. Applying the binary
does restart the selected core process and can interrupt its active connections.
Use the sequential fleet updater when selecting multiple cores rather than
manually restarting the entire fleet simultaneously.

After installation, verify the reported version and binary digest, a fresh
heartbeat, matching desired/applied manifest revisions and no apply error.
Confirm successful routing synchronization as well. The updater retains its
previous-binary recovery path if candidate health verification fails.
Rolling back to v1.6.11 also restores that release's route-refresh expiry
behavior.

## Scope

This is a core routing-lifecycle release. Host infrastructure management and
panel frontend/backend changes are separate concerns and are not included.
The availability change applies to published routing decisions, not to the
independent authorization and resource limits described above.
